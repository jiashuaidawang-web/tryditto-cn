## 三、衔接设计：现有「收集信息」→ AI 链路（字段级）

```
questions.json / questions.ts（单一来源，不动）
        ↓ AnswerValidator.validate
onboarding_answer（逐题写穿，不动）
        ↓ ProfileProjector.project(answers, catalog)
profile 行（结构化投影，不动）
        ↓ 【新增 Step 3】TasteExtractor（异步，入驻完成/编辑文字题/反馈后触发）
user_taste（version, persona_text, taste_text, embedding_id, embedding_version）
        ↓ 【新增 Step 4】VectorSync → Qdrant（taste/persona/tags/crush 多向量）
        ↓ 【新增 Step 5】AiRankService：分身模拟 + 裁判 → Map<PairKey,Integer> aiScore
MatchingInput（新增可选 aiScores，默认空 → 现有 404 测试零影响）
        ↓ MatchingSolver（Blossom，AI 分只进 objective 目标函数，不进 score/门槛/展示分）
match / match_copy（AI 文案经 CopyValidator，失败模板兜底）
        ↓ MatchFlow.feedback（不动）
        ↓ 【新增 Step 7】TasteRewriter（每周≤1次、单次1权重、版本化可回滚）
user_taste 新版本 → 下一周期召回与精排生效
```

**三条硬原则**：
1. **AI 分只进目标函数**（与 M2-domain 笔记"公平加分只进 objective 不进 score/门槛"完全一致），硬约束、风格门槛、一人一位、确定性等 379 条不变量全部不动
2. **不新建问卷体系**：taste 的输入是 `answers` + `profile` + `feedback`，全部来自现有链路
3. **不改 `users-v1.json`**：隐藏真值、Oracle 配置放 `sim/hidden-truth-v1.json` 侧车，`SyntheticFixtureTest` 逐字节断言不受影响

## 四、必须一次性核对的冲突（最重要）

`docs/技术方案.md` §8.1 原文：**「大模型不决定谁和谁配对，不选地点以外的东西，不看照片」**，且 §8.2 流水线前 5 节点全是纯 Java 规则，`copyAll` 只在配对**之后**跑文案。

我的 v3 方案要求"双方真人分身互约 + 裁判打分"，本质是让 LLM 参与配对排序。两者边界不同：

- 若**严格按 §8.1**：我的 Agent 精排不能落地，v3 只剩向量召回 + 反馈学习 + 仿真
- 若**按 v3 全量**：需要正式修订 §8.1，把边界改成"LLM 不决定**可行性**（硬约束/门槛），但可以提供目标函数里的契合分"
- 我推荐的折中（见核对问题 Q1）：**AI 分只进 objective**，既实现"化学反应可预测"，又完整保留 379 测试钉住的全部安全不变量，改动面最小

# 十四、镜像阻塞的解决路径（我自己推进，不需要再决策）
