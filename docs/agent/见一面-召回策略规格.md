# 「见一面」召回策略规格（上线前打磨版）

> 配套：`见一面-后端匹配机制方案设计v3.md`
> 定位：召回是匹配系统的命门。初筛错了，后面的 Agent 精排再强也是在错候选里挑最优。本文给出可在**上线前用合成数据反复打磨、可量化验收**的完整召回方案。
> 日期：2026-11-15

---

## 一、为什么必须上独立向量库（实测证据，不是偏好）

### 1.1 pgvector HNSW 的 post-filter 塌陷

pgvector 的 HNSW 是**先取 ef_search 个近似近邻，再套 WHERE 过滤**。过滤越严， surviving 结果越少，且不报错、不告警。公开基准（100K 向量、PostgreSQL 18.6 + pgvector 0.8.7、`LIMIT 10`、无迭代扫描）：

| 过滤选择性 | 实际返回行数 | Recall@10 |
|---|---|---|
| 50% | 10.00 | 0.939 |
| 10% | **3.99** | **0.398** |
| 1% | **0.39** | **0.039** |
| 0.1% | **0.03** | **0.003** |

开启 `hnsw.iterative_scan = relaxed_order` 后能补到 10 行，但 0.1% 桶 Recall 仍只有 0.791、延迟从 2.7ms 涨到 69ms；且 `ef_search` 默认 40，`LIMIT 50` 时最多只能返回 40 行（静默少 20%）。

**我们的硬过滤选择性正好落在 1-10%**：同校（单校 / 多校 ≈ 1-20%）× 性别配对（≈50%）× 等时圈可达（≈30-60%）× dealbreaker 排除 × 已配过/拉黑排除。复合后经常 <5%。按 v2 的方案，**候选池会被悄悄抽空，线上监控还看不出来**——这是不可接受的。

### 1.2 除了过滤，还有四个必须项

| 需求 | pgvector 单表 | 专用向量库 |
|---|---|---|
| 过滤在图遍历时生效（pre-filter / filterable HNSW） | 需 0.8+ 迭代扫描补救 | 原生 |
| 多向量（口味/人格/审美各自一路） | 需多列多索引，融合在应用层 | named vectors 原生 |
| 稀疏 BM25 + 稠密混合、服务端 RRF | 需自建 tsvector + 应用层融合 | 原生 |
| 按过滤选择性分桶做离线 Recall 评测 | 需自己造 ground truth | FLAT 精确检索即 ground truth |
| embedding 模型升级的双写/影子/切流 | 手工 | 多 collection 天然支持 |

### 1.3 选型：Qdrant 主召回 + pgvector 影子精确对照

VectorDBBench（Cohere 1M / 768d / 过滤保留 1%）：Qdrant Cloud recall **1.0**（P99 7.0ms），Milvus recall 0.9507（P99 1.6ms），Zilliz 0.9788。Qdrant 的 **filterable HNSW** 把 payload 索引并入图遍历（额外连边 + bitset 掩码），高选择性过滤下仍保持召回；单 Docker 可跑，运维面最小；Java SDK、named vectors、稀疏 BM25、服务端 RRF 齐备。

- **主**：Qdrant（单机起步，集群按需）
- **影子**：pgvector FLAT（不开 ANN）或 Qdrant FLAT collection，**只算 ground truth**，不服务在线
- **迁移路径**：千万级以上 / 多校 K8s 分片时评估 Milvus；业务层统一走 `RecallService`，换引擎不改业务代码
- **诚实说明**：纯规模角度单校几百人 pgvector 完全够用；上独立库不是为了规模，是为了**过滤下的召回质量 + 多路融合 + 可离线评测 + 可灰度切流**这四件事，这些必须在上线前就位

## 二、Collection 设计

**collection**：`match_user_v{N}`（N 跟随 embedding 模型版本，禁止跨版本混算）

**named vectors**

| 字段 | 维度 | 距离 | 来源 | 用途 |
|---|---|---|---|---|
| `taste` | 1024 | Cosine | `mp_persona.taste_text`（口味/想要什么） | R1 主语义召回 |
| `persona` | 1024 | Cosine | `mp_persona.persona_text`（我是什么人） | R2 人格共鸣召回 |
| `crush` | 512 | Cosine | 明星 crush 图像 → 图像 embedding（可选） | R4 审美召回 |
| `tags`（sparse） | 词表 | BM25 | 兴趣/价值观/dealbreaker 标签、问卷关键词 | R3 稀疏与精确标签召回 |

> `taste` 与 `persona` 必须分开：用户嘴上说要什么，和这个人本身是什么气质，是两回事。Ditto 的核心主张（化学反应来自人格共振）要求两路独立可归因。

**payload（全部建索引）**

```
user_id            integer
school_code        keyword      ← partition/隔离键
campus_code        keyword
gender             keyword
expected_gender    keyword[]
age                integer
height_cm          integer
iso_cells          keyword[]    ← 等时圈网格 id，可达性用数组交集判断
interest_tags      keyword[]
value_tags         keyword[]
dealbreaker_tags   keyword[]
mbti               keyword
look_weight        float        ← 兴趣优先/外貌优先
starve_weeks       integer      ← 饥饿优先
new_user           bool
verified           bool         ← 学籍+人脸双认证
photo_approved     bool
is_active          bool
is_synthetic       bool         ← 仿真数据隔离
embedding_version  keyword
last_active_cycle  keyword
```

**HNSW 参数起点**（调优见第五节）：`m=32`、`ef_construct=200`、`hnsw_ef=128`、`on_disk_payload=true`、`full_scan_threshold` 按选择性兜底。
**payload index**：`school_code / gender / age / height_cm / iso_cells / starve_weeks / is_active / verified / embedding_version` 全部建索引，否则 Qdrant 会退化为全量扫描。

## 三、五路召回器（每路独立开关、独立配权、带归因）

| 路 | 名称 | 检索 | TopK | 失败降级 |
|---|---|---|---|---|
| **R1** | 口味语义 | `taste` 稠密 ANN + 硬过滤 | 200 | 降为结构化标签召回 |
| **R2** | 人格共鸣 | `persona` 稠密 ANN + 硬过滤 | 200 | 并入 R1 加权 |
| **R3** | 稀疏/标签 | `tags` BM25 + 兴趣/价值观/dealbreaker 精确匹配 | 200 | 结构化 SQL 兜底 |
| **R4** | 审美多模态 | `crush` × 对方照片 embedding | 100 | 仅在双方照片过审且 `look_weight>阈值` 时启用；失败直接跳过 |
| **R5** | 探索/公平 | `starve_weeks` 降序 + 新用户配额 + 随机受控探索 | 50 | 永不降级（长尾保底） |

### 3.1 硬过滤下沉到 Qdrant（关键）

所有硬约束写进 `filter`，**不是召回后再过滤**：

```
must:    school_code == 本校
         is_active == true
         verified == true
         photo_approved == true
         gender ∈ 用户期望 && expected_gender 包含用户性别
         age BETWEEN [age_min, age_max]
         height_cm BETWEEN [height_min, height_max]（若用户设了）
         iso_cells ANY IN 用户可达网格
         embedding_version == 当前版本
must_not: has_id IN forbidden_user_ids   ← 已配过 / 拒绝 / 拉黑 / 注销 / 封禁
```

`forbidden_user_ids` 由 `mp_pair_memory.forbidden` + 拉黑表实时生成，单用户通常几十个，走 `has_id` 开销可忽略。**注销用户必须同时从 Qdrant 删除**，不能只靠 filter（数据最小化要求）。

### 3.2 融合

```
score(d) = Σ_i  w_i · 1 / (k + rank_i(d))     # RRF, k = 60
```
- 初始权重 `w = {R1:1.0, R2:0.9, R3:0.7, R4:0.4, R5:0.6}`，**上线前用回放实验网格搜索确定**，不拍脑袋
- 去重后按 RRF 排序；每个候选保留 `sources[]` 供归因
- **保底机制**：融合后候选 < `MIN_CANDIDATES=50` 时，按序 ① 提高 `hnsw_ef` 至 256/512 重查 ② 放宽 `score_threshold` ③ 启用同校结构化兜底 ④ 仍不足写 `recall_shortfall` 告警并让该用户本周走保守配对（宁缺毋滥）
- **单路占比上限 60%**：任一路贡献超过 60% 触发告警，说明其他路失效

### 3.3 粗排（召回 → Top15）

```
coarse = 0.40·条件契合(硬条件+dealbreaker余量)
       + 0.30·RRF 归一化排名
       + 0.10·曝光公平(starve_weeks)
       + 0.20·反馈历史(同类反馈的偏好修正项)
```
Top15 进 Agent 精排。**粗排结果必须保留**，是 LLM 全挂时的交付兜底。

## 四、ANN 参数调优（上线前必做，不是上线后）

### 4.1 Ground truth 定义

同一 `filter`、同一 query，在 **FLAT 精确 collection** 上跑全量余弦得到 exact topK；ANN 结果与之比：

```
Recall@K = |ANN_topK ∩ exact_topK| / K
```
**必须分选择性桶测**：0.1% / 1% / 5% / 10% / 50%，每桶至少 200 个 query（从合成用户里抽，覆盖长尾）。只看全局平均值会掩盖最脆弱的用户群体——而这些往往是最需要被照顾的人。

### 4.2 参数扫描

| 参数 | 扫描值 | 影响 |
|---|---|---|
| `hnsw_ef` | 64 / 128 / 256 / 512 | 查询期候选预算，直接影响 recall 与 p99 |
| `m` | 16 / 32 / 64 | 图连通度，重建成本高，先定后不动 |
| `ef_construct` | 100 / 200 / 400 | 建图质量 |
| `score_threshold` | 关闭 / 0.2 / 0.35 | 过严会加剧短召回 |
| `oversampling` | 1.0 / 1.5 / 2.0 | 过滤后补足候选 |

判定：**在满足各桶 Recall@50 ≥0.95（1% 桶 ≥0.90）的前提下，取 p99 延迟最小的参数组合**。把扫描结果固化成配置文件，写进上线闸门材料。

### 4.3 常见坑（逐项验证）

- `LIMIT > ef` 导致静默少结果（pgvector 默认 ef=40，Qdrant 同理要显式设 `hnsw_ef >= limit`）
- 过滤列没建 payload index → 退化全表扫描，测试环境数据少看不出来，上线才暴露
- 数组字段 `iso_cells` 未正确建 keyword 索引 → 等时圈约束形同虚设
- `embedding_version` 混算 → 新旧向量余弦不可比
- 注销只改 PG 不改向量库 → 已注销用户仍被召回
- 只在小数据集上测 → planner 走精确扫描，"测试通过但什么都没验证"

## 五、离线评测指标与实验矩阵

### 5.1 指标（仿真与灰度同一套实现）

| 指标 | 定义 | 目标 |
|---|---|---|
| Recall@50 / @200 | 对照 FLAT 精确结果 | ≥0.95 / ≥0.98 |
| Filtered Recall@50 | 1% 选择性桶 | ≥0.90 |
| 候选覆盖率 | 有 ≥50 个有效候选的用户占比 | ≥98% |
| 来源多样性 | 候选平均覆盖路数 / 标签熵 | ≥2.5 路 |
| 长尾曝光率 | 最不活跃 20% 用户的曝光份额 | ≥人数占比的 80% |
| 单路依赖 | 任一路贡献占比 | ≤60% |
| 冷启动召回质量 | 零反馈用户的 top15 命中真实合拍比例 | ≥35% |
| 重复率 | 同一 pair / 已拉黑 | 0 |
| 延迟 | p50 / p99 | 按闸门表 |

### 5.2 上线前实验矩阵（全部在阶段 B 跑完）

| # | 实验 | 目的 |
|---|---|---|
| E1 | 五路全开（基线） | 基线指标 |
| E2-E6 | 逐路消融（关掉一路） | 验证每路有非零贡献，确定权重 |
| E7 | RRF k ∈ {20,60,120} | 融合参数 |
| E8 | 权重网格搜索 | 定最终 `w_i` |
| E9 | `hnsw_ef` × 选择性桶扫描 | 定 ANN 参数 |
| E10 | 纯 R1 单路 vs 五路 | 证明多路必要，量化提升 |
| E11 | 有/无 R5 探索路 | 验证长尾曝光保障 |
| E12 | 旧 embedding 模型 vs 新模型（影子） | 决定是否切流 |
| E13 | 池子规模 100 / 500 / 2000 / 10000 | 验证扩校后不劣化 |
| E14 | 过滤极端选择性（0.1% 桶） | 最脆弱用户群体 |

每组实验在**同一批合成用户、同一 12 周期回放**上跑，结果写 `sim_run` 表，可复现。

## 六、embedding 模型版本迁移（上线后也会反复发生）

1. 新建 `match_user_v{N+1}`，`VectorSyncService` 双写（PG 存 `embedding_version`）
2. 影子检索：在线仍用 vN，vN+1 只跑离线回放与精确对照
3. E12 实验通过（各桶 Recall 不劣化、长尾曝光不降、末周期命中率提升 ≥3%）才允许切流
4. 灰度切流按用户 1% → 10% → 50% → 100%，每档观察 1 个完整周期
5. 任一指标恶化 >5% 立即回滚到 vN（双写期间可秒切）
6. 旧 collection 保留 2 个周期后清理

**禁止跨版本计算相似度**；payload 里 `embedding_version` 是硬过滤项。

## 七、召回专项上线闸门（并入 v3 第五节 Go/No-Go）

| 检查项 | 阈值 |
|---|---|
| 各选择性桶 Recall@50 | 50%/10%/5%/1% 桶 ≥0.95；0.1% 桶 ≥0.85 |
| 候选覆盖率 | ≥98% 用户有 ≥50 有效候选 |
| 五路贡献 | 每路非零，单路 ≤60% |
| 消融实验 | 关闭任一路都有可测量的指标下降（证明不是凑数） |
| 长尾曝光 | 达标（见 5.1） |
| 注销/拉黑 | 向量库删除 + 回放验证不得召回，100% |
| Qdrant 不可用演练 | 降级到结构化召回，仍能在 18:00 前交付 |
| 参数配置 | 扫描结果固化入库，可一键回滚 |
| 影子对照 | 每日自动产出 Recall 曲线，告警已配置 |

---

## 八、在线监控（上线后持续，不是一次性）

- 每日低峰跑影子精确对照，输出分桶 Recall 曲线；连续 2 天下降 >3% 报警
- `recall_shortfall` 次数/用户数、单路占比、p99、`hnsw_ef` 实际值
- embedding 漂移：`taste` 重写后向量变化幅度分布，异常放大报警
- 每次模型/参数/权重变更都走一遍 E1-E14 的子集回放，禁止热改配置直接上线

## 九、Qdrant 检索请求骨架（Java 侧伪代码）

```java
Filter f = Filter.newBuilder()
    .addMust(matchKeyword("school_code", school))
    .addMust(matchBool("is_active", true))
    .addMust(matchBool("verified", true))
    .addMust(matchBool("photo_approved", true))
    .addMust(matchIntRange("age", ageMin, ageMax))
    .addMust(matchAny("iso_cells", reachableCells))
    .addMust(matchKeyword("embedding_version", CUR_VERSION))
    .addMustNot(hasId(forbiddenIds))          // 已配过/拒绝/拉黑/注销
    .build();

SearchPoints r1 = qdrant.search("match_user_v1", queryTasteVec, "taste",
                    f, /*limit*/ 200, withHnswEf(256), withPayload(true));
// R2 persona / R3 sparse BM25 / R4 crush / R5 starve 同理，各自带同一 filter
List<Cand> fused = RRF.merge(List.of(r1, r2, r3, r4, r5), k(60), weights);
if (fused.size() < MIN_CANDIDATES) fused = fallbackAndAlert(userId, f);
return coarseRank(fused).top(15);
```

> 同一 `filter` 必须复用于五路与 FLAT 精确对照，否则 Recall 指标无意义。
