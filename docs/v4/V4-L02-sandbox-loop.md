# V4-L02 沙箱闭环

一条闭环是：当前工作区用户池、策略 E 的候选图、M02 双向评分、只把推荐合格边交给 M04、选择一对 `COMPLETE` 且安全复查通过的配对、双方反馈、F02 提案、用户本人确认、新版画像、新的全局匹配运行。

案例：

| 案例 | 做什么 | 标记 |
| --- | --- | --- |
| A | 数学夹具上 G0 和 G2 配对不同 | `MATH_COMPARE`，只读对照，不能进入反馈 |
| B | 一方接受、另一方拒绝 | `ENGINE_EXECUTED`。不生成确定性偏好 |
| C | 双方接受 | 账本派生 `MUTUAL_ACCEPTANCE_REACHED` |
| D | 双方出席报告相反 | 投影保持 `CONTESTED` |
| E | 用户明确选择自己的软偏好后重新匹配 | 这个值不是从接受事件推断的。画像版本增加，新运行的 `parentRunId` 指向旧运行 |
| F | 撤回刚才的确认来源 | 该偏好退出评分，其他特征还在，不恢复整份旧画像 |

冻结的 M04、F01、F02 案例目录仍是 `FROZEN_RESULT`。上面六组是这次工作区里的实际执行。旧匹配快照保存在 `LabRun.inputSnapshot`，随后修改当前画像不会改写它。G1 运行打开的反馈携带 `global-objective-g1-1`，G2 运行携带 `global-objective-g2-1`。

确认一条软偏好时，学习适配器只替换带 `confirm.` 来源的特征。不能作为学习种子的行为、硬约束和未确认特征留在原画像上。直接编辑之后，证据缓存按新版本重建，不会用旧证据覆盖这次编辑。
