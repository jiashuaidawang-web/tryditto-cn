# 04 技术选型

调研日期：2026-11-12。价格与能力以当日能打开的官方文档为准，厂商可随时改价。本文只做选型，不写实现。

证据等级：

- 【已证实】：本轮打开的官方文档、价格页或法规原文里有对应表述。
- 【推断】：由已证实事实加上产品约束推出来的工程取舍，不是厂商承诺。
- 【猜测】：没有可用出处，只标出风险，不进入推荐和成本合计。

范围：独立 H5，中国大陆部署，edu.cn 邮箱证明在校学生。不依赖微信。第一阶段不做 App。周三 19:00 批量匹配，每人至多一个本校对象。

## 1. 每周推送

事实源必须是站内「本周匹配」页。推送只负责把人叫回来。任何通道都可能失败，打开 H5 仍能看到结果。【推断】

华为 Push Kit 面向已集成 SDK 的安卓应用、iOS 应用，以及他们自己的网页推送；网页推送要在 AppGallery Connect 选择数据存储地。来源：<https://developer.huawei.com/consumer/cn/doc/agc_Pushservice_Introduction>。第一阶段的独立 H5 用不了「装进 App 的厂商通道」。【已证实】

### 1.2 取舍

- 只靠用户记得周三打开：零成本，到达率取决于习惯。【推断】不适合作为唯一方案。
- 只靠 edu.cn 邮件：单价约 0.002 元/封，但校园网关、垃圾邮件夹和延迟都在我们控制之外。阿里云计的是自己入信成功，不是学生真的看见。【已证实计费口径；到达率未查到数字】
- 只靠 Web Push：iPhone 用户必须先「添加到主屏幕」再点订阅。国内大量默认浏览器没有可引用的 Push API 支持。不能把周三到达率押在这条上。【推断】
- 短信：要额外收集手机号，有签名报备周期，但是本轮能查到的、不依赖微信和 App 的唯一「系统级、到点、按条计费」通道。19:00 在通知短信允许发送的时段内。【推断：用通知模板而不是推广模板】

官方文档没有给出短信、邮件或 Web Push 的到达率百分比。下面不写任何到达率数字。

### 1.3 推荐

1. 注册时同时要 edu.cn 邮箱和手机号。邮箱证明学校，手机号承担账号真实身份的一种法定方式和周三通知。身份规定见第 6 节。
2. 周三 19:00 发一条 70 字以内的通知短信，只写「本周匹配已生成」和短链。邮件并行发一封摘要，当作备份，不当作主通道。
3. H5 检测 `PushManager`。仅在 Chrome / Edge / Firefox，或 iOS 16.4+ 的主屏幕 Web 应用里请求通知。不支持就不要反复弹。
4. App 阶段再接华为、小米、OPPO、vivo、荣耀的厂商通道。聚合 SDK 也要等有原生包之后。

### 2.2 三个任务分别用谁

照片理解只抽可核对的描述：场景、穿搭风格、照片是否清晰、是否有联系方式或二维码。不打颜值分，也不把外貌向量当作匹配目标。外貌排序会把偏见写进每周结果，也更容易碰到敏感个人信息。【推断】

| 任务 | 推荐 | 不用谁 | 理由 |
| --- | --- | --- | --- |
| 对话式问卷 | 主：`deepseek-flash` 非思考模式，Json Output。备：`qwen-plus` 非思考，或 `qwen3.7-plus` 的 JSON Schema | Kimi K3 不作为主对话模型 | 闲时输出 4 元/百万 tokens，上下文 1M，足够多轮问卷。周三高峰不在 19:00。Kimi 在方舟上的转售输出价是 68 元，贵一个数量级。智谱免费 Flash 适合开发和评测，免费档限额未抄到，不作为唯一生产依赖 |
| 性格画像抽取 | 问卷结束后单独一次调用。优先 `qwen3.7-plus` JSON Schema；DeepSeek 可以做，但必须用本地 schema 校验 | 不在每一轮闲聊里抽画像 | 百炼文档写明 JSON Schema 能约束字段。多轮对话若每轮都抽，输出 token 和解析失败都会上去。画像失败就重试或改由用户确认，不把残缺 JSON 写入匹配 |
| 看照片 | 主：`deepseek-flash`。标签不稳再换 `qwen3-vl-plus` 非思考 + JSON Object，本地再校验 | 不用文生图模型「评价」真人；不用免费视觉档当生产唯一路径 | 单图最多约 1024 tokens，三张照片的输入费用在 Flash 闲时是分钱级。`qwen3-vl-plus` 输出 10 元/百万 tokens，只在 Flash 的标签不稳定时加调用。多模态走不了 strict JSON Schema |
| 匹配理由 | `deepseek-flash`，周三 19:00 闲时，批量生成 | 不用旗舰模型写理由 | 配对已经由算法定死。模型只根据双方已有结构化字段写 100–150 字，禁止编造共同经历。输出短，闲时 4 元/百万 tokens |

内容安全不靠模型自觉。用户原文、模型输出、照片都再过第 6 节的审核 API。百炼护栏只覆盖走百炼的调用。【推断】

## 3. 匹配算法

产品约束：同一学校、每周一次、每人至多一个对象、双方取向必须相容、不重复配已见过的人、可以有年级窗口、配不上就宁缺。约时间发生在配对之后，不作为配对输入。

### 3.1 候选

| 方法 | 能保证什么 | 不适合直接当 MVP 的原因 |
| --- | --- | --- |
| 画像向量召回 + LLM 重排 | 人多时能缩小候选 | 单校每周几百到几千人，硬过滤之后可以全量打分，不必先上近似最近邻。LLM 重排不能保证「每人至多一个」和「不重复」，还会把同一对人的顺序跑飘 |
| Gale-Shapley 稳定匹配 | 双边列表下没有不稳定对。经典问题见 Gale 与 Shapley，1962，*College Admissions and the Stability of Marriage*。综述：<https://zh.wikipedia.org/wiki/%E7%A8%B3%E5%AE%9A%E5%A9%9A%E5%A7%BB%E9%97%AE%E9%A2%98> | 标准形式是男女二分图。本校若同时有异性恋、同性恋、双性恋，图不是二分图，经典 Gale-Shapley 套不上。提议方顺序也会系统性地让一方更占优 |
| 最大权二分图匹配 | 异性恋池里，边权之和最大，且每人至多一条边 | 同样假设二分图。匈牙利算法或最小费用流可以做。混合取向要换成一般图匹配 |
| 带约束的整数规划 | 每人至多一条边、最低分数、历史互斥、阻断、年级，都可以写成约束。Google OR-Tools CP-SAT：<https://developers.google.com/optimization/cp/cp_solver> | 实现和测试成本高于「先过滤再贪心」，但单校规模下这个成本值得付。它是混合取向时仍然正确的做法 |

pgvector 提供 Postgres 里的精确和近似向量检索：<https://github.com/pgvector/pgvector>。【已证实该扩展存在】单校 MVP 不必为了召回先依赖它。【推断】

### 3.2 冷启动、性别比、反馈

- 冷启动：前几周没有见面反馈。权重只用问卷里的显式字段，例如年级窗口、作息、想找的关系、兴趣重合、明确的拒绝项。不使用外貌相似度。【推断】
- 性别或取向失衡：匹配人数的上限是「还能连上边的较稀缺一侧」。强行配满会把低于阈值的边放进去。低于最低分的边直接删掉，剩下的人收到「本周没有足够合适的人」。【推断】
- 第二遍只放宽年级窗口之类事先写明的软约束，不放宽取向、拉黑和历史已匹配。【推断】
- 反馈：见面后记「见面了没有、愿不愿意再约」。下一周用这些样本拟合一个很小的线性权重，加到边权上。不在 MVP 微调大模型，也不做在线强化学习。一个学校反馈太少时，权重保持默认值。【推断】

### 3.3 MVP 推荐

每个学校、每周三 19:00 之前：

1. 取出本周可参与的人：邮箱已验证、问卷完整、照片已通过审核、未封禁、本周选择参与。
2. 两人之间没有边，如果：取向不相容、任一方拉黑、历史上已匹配过、年级差超出当前窗口、任一方低于最低完整度。
3. 边权是显式字段的加权和，减掉拒绝项。权重写在配置里，并有单元测试锁定。
4. 用 CP-SAT 求最大权匹配，约束是每个点至多一条边，边权低于阈值的不进入模型。
5. 配对锁定之后，再调用 `deepseek-flash` 写理由。模型不能改配对。
6. 自由文本简介变长、或单池大到全量打分不合适时，再把简介嵌成向量，用 pgvector 取每个用户的前若干候选，整数规划只在这些边上做。向量是 v1.1，不是第一周的阻塞项。

一般图上的最大权匹配也可用 Edmonds 算法。MVP 仍选 CP-SAT，因为后面加「最低分、名额、互斥」时不用换算法。【推断】单校一两千人、每人只保留几十字段的边，这个规模对 CP-SAT 是小问题。【推断，未做基准测试】

### 5.2 真人校验要不要上

本校交友 H5 会发布头像、简介，并在约时间时交换信息。把它看成第九条里的服务，是合规上的稳妥读法，不是律师意见。【推断】edu.cn 邮箱不在第九条列举的三种方式里。邮箱证明「这个学校的邮箱」，不代替手机号或证件号。【推断】

阿里云金融级实人认证，H5 可以接入。来源：<https://help.aliyun.com/zh/id-verification/financial-grade-id-verification/product-overview/billing-overview>。【已证实】

| 方案 | 标准价 | 证明什么 |
| --- | --- | --- |
| 金融级实人认证（姓名+身份证+活体人脸） | 1 元/次 | 证件本人，且是真人 |
| 金融级活体检测，H5 | 0.182 元/次 | 当前操作者是真人，不核验证件 |
| 金融级人脸比对，服务端 | 0.006 元/次 | 两张脸是否同一人，不核验证件 |
| 另一套 AI 实人认证里的活体检测 | 0.2 元/次 | 见 <https://help.aliyun.com/zh/id-verification/ai-real-person-verification/product-overview/billing> |

阿里云 FAQ 把「金融级活体检测」的例子写成真人社交注册：证明是真人，不证明身份证件。来源：<https://help.aliyun.com/zh/id-verification/financial-grade-id-verification/support/faq>。【已证实】

MVP：edu.cn 邮箱 + 手机号 + 满 18 岁声明。不上 1 元/次的人证合一。照片侧用内容审核挡裸露、二维码和广告，不做人脸打分。

下一阶段，若假照片成为主要投诉，再加 H5 活体检测（0.182 元/次），并在单独同意里说明这是生物识别。人脸比对只用于「活体帧和本人上传的照片是不是同一个人」，不把人脸特征拿去排序。【推断】

不满 18 岁的本科生可能存在。注册声明未满 18 岁则拒绝服务。这是产品约束，不是本轮查到的专项许可条款。【推断】

### 5.3 防骚扰和防诈骗

这些是产品规则，不是某一家 API 的功能。【推断】

- 每周每人最多一个新对象。没有开放的陌生人私信。
- 见面时间和地点由系统在双方提交的空档里取交集，地点用预设的校园公开场所列表，不收集家庭住址。
- 简介和照片里的手机号、微信号、二维码、外链，审核命中就拒绝或打回。
- 拉黑、举报、未见面爽约记录进下一周的硬约束。
- 同一手机号、同一邮箱、同一设备的重复注册要限频。设备指纹可以用审核接口可选的 `deviceId`，但不要为了风控去买一套未评估的探针 SDK。
- 匹配理由和海报在展示前过文本审核。审核失败就改用固定模板句，不把未审核文本发给对方。

## 7. 让多个 AI 编码代理写对

选型原则：代理要靠编译器和测试发现自己错了，而不是靠人读 diff。

| 选择 | 为什么对代理友好 |
| --- | --- |
| TypeScript `strict`，禁止 `any` | 字段写错会在生成代码时失败，而不是在周三批处理时失败 |
| Zod（或同类）作为唯一 schema | 问卷、API、数据库写入、模型 JSON 共用一套。模型输出先过 schema 再入库。代理可以为解析器写失败用例 |
| 匹配逻辑放在纯函数 | 输入是候选人列表，输出是配对列表。不连数据库、不调模型。pytest 或 Vitest 用固定夹具锁定「互斥、重复配对、性别失衡、低于阈值则宁缺」 |
| Python 只负责匹配作业 | OR-Tools 的 CP-SAT 文档和示例以 Python 为主。其余仍用 TypeScript，避免两套业务类型 |
| Vitest 测单页和纯函数；Playwright 测注册、问卷、看到匹配、提交空档 | Playwright 官方：<https://playwright.dev/>。端到端用脚本起本地服务和测试数据库，不依赖人手点 |
| 一个仓库、一个 `docker compose`（Postgres，预装 pgvector） | 代理不需要猜远程环境。集成测试可以真的插入两个人再跑一轮匹配 |
| 业务规则写成测试名称，不写在聊天记录里 | 例如「已匹配过的两人本周没有边」。后来的代理改权重时测试会失败 |

不把第一版拆成多个微服务。代理跨服务改契约时最容易各写各的。H5、API、审核、发信放在一个 TypeScript 应用里；只有匹配脚本是第二个进程，并且它读的表结构由迁移文件生成。【推断】

海报模板用 Playwright 打开夹具页并截图对比。这样「改 CSS」和「端到端测试」用的是同一个浏览器，而不是 Satori 的另一套布局引擎。【推断】

## 10. 信息缺口

- 短信、edu.cn 邮件、Web Push 都没有可引用的到达率百分比。校园邮要做目标学校实测。
- 国内厂商浏览器对 W3C Push API 没有官方「支持」或「不支持」的结论，只有「文档未证明」。
- iOS 16.4 以上的在网占比，本轮没有可靠统计。限制本身不取决于占比：没添加到主屏幕就收不到。
- Kimi 国内站人民币单价表，本次页面抓取没有渲染出来。豆包价格页没有单独的视觉理解对话单价。
- 智谱免费模型的 RPM/TPM，以及 DeepSeek Json Output 是否等于 strict JSON Schema，页面没写清。
- 通义万相按张价格、网易易盾的元/系数、腾讯云短信单价，本轮未抄到。
- 阿里云 ECS / RDS 的目录月费只在购买页生成，社区活动价已丢弃。
- 备案号与「当前这个模型版本」是否同一条，要向厂商确认。豆包备案号未用官方页核实。
- 第九条是否必然覆盖「只有匹配、没有开放私信」的形态，需要律师确认。本文件按「会发布头像和简介」做了稳妥处理。
- CP-SAT 在真实学校数据上的耗时没有基准。规模判断是推断。
- 各模型对「描述穿搭」和「拒绝给真人打分」的实际服从度，要做一批照片评测，不能从价格页得知。
